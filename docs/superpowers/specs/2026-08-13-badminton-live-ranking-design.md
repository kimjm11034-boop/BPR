# 배드민턴 실시간 경기 기록 앱 설계

## 1. 목표와 범위

휴대폰에서 복식 경기의 네 선수를 선택하고 승리팀을 지정하면 개인 누적 전적, 파트너 조합별 전적, 당일 경기 기록이 즉시 갱신되는 모바일 우선 앱을 만든다. Supabase를 유일한 원본 데이터로 사용하고, Google Sheets는 사람이 열람하고 백업할 수 있는 비동기 복사본으로 유지한다.

첫 버전에 포함하는 기능은 다음과 같다.

- 선수 추가 및 활성/비활성 관리
- 파트너가 매 경기 달라질 수 있는 복식 경기 입력
- 승리팀 선택 후 경기 확정
- 당일 경기 목록과 누적 경기 목록 조회
- 개인 누적 순위와 파트너 조합 순위 조회
- Supabase Realtime을 통한 여러 휴대폰의 자동 갱신
- Google Sheets 경기 기록 자동 동기화와 실패 재시도
- 잘못 입력한 경기의 수정 또는 취소

개인별 회원 계정, 푸시 알림, 점수 세트 기록, 대진 자동 편성, 오프라인 신규 경기 저장은 첫 버전에서 제외한다. 운영자는 공유된 운영용 접근 코드로 로그인해 서명된 HttpOnly 세션 쿠키를 발급받으며, 쓰기 작업은 이 운영자 세션이 있는 경우에만 허용한다.

## 2. 확정된 제품 원칙

- 종목은 2대2 복식이며 파트너는 경기마다 바뀔 수 있다.
- 순위의 기본 단위는 고정 팀이 아니라 선수 개인이다.
- 주 순위 기준은 승률이다.
- 파트너 조합 전적은 개인 순위와 별도로 제공한다.
- 모든 파트너 조합은 첫 경기부터 표시한다.
- 조합 경기 수가 1~2회이면 `경기 수 적음` 배지를 표시하고, 3회부터 제거한다.
- 한 경기의 네 자리에는 서로 다른 선수만 들어갈 수 있다.
- 선수는 이름이 아니라 변경되지 않는 UUID로 식별한다.
- 현재 동명이인은 없지만, 향후 동명이인이 추가되면 회원번호로 구분한다.
- 경기 결과 입력과 수정은 앱에서만 수행하며 Google Sheets는 읽기 및 백업 용도다.

## 3. 사용자 흐름과 화면

### 3.1 오늘 화면

오늘 날짜의 세션 요약, `새 경기 시작`, 최근 완료 경기, 상위 개인 순위를 한 화면에 보여준다. 선택된 3번 디자인을 기준으로 초록색 배드민턴 코트 이미지를 큰 배경으로 사용하고, 흰색 입체 카드와 얕은 그림자로 정보를 구분한다.

완료 경기 행에서는 기존의 `왼쪽 팀 승리` 또는 `오른쪽 팀 승리` 문구를 사용하지 않는다. 승리한 두 선수 영역을 둥근 사각형으로 감싸고, 테두리 왼쪽 위에 작은 `승` 배지를 겹쳐 붙인다. 패배팀은 기본 스타일로 남겨 한눈에 결과를 구분할 수 있게 한다.

### 3.2 경기 입력

1. A팀 선수 2명과 B팀 선수 2명을 검색 또는 목록에서 선택한다.
2. 이미 선택된 선수는 나머지 세 자리에서 비활성화한다.
3. A팀 또는 B팀을 승리팀으로 선택한다.
4. 저장 직전에 네 선수, 팀 구성, 승리팀을 확인한다.
5. 확정하면 오늘 경기 기록으로 이동하고 순위가 갱신된다.

저장 버튼은 네 명의 고유 선수와 승리팀이 모두 선택된 경우에만 활성화한다. 빠른 연속 탭에 의한 중복 저장은 클라이언트 요청 ID와 서버의 고유 제약으로 차단한다.

### 3.3 기록

기본 화면은 오늘 완료된 경기를 최신순으로 보여준다. 날짜를 선택하면 과거 세션을 볼 수 있고, 각 경기에는 시간, 두 팀, 승리팀 표시, Google Sheets 동기화 상태를 제공한다. 운영자는 경기를 수정하거나 취소할 수 있다. 취소는 물리 삭제가 아니라 상태 변경으로 처리해 감사 기록과 시트 정정 이력을 남긴다.

### 3.4 순위

상단 탭은 `개인 순위 | 파트너 조합`으로 구성한다.

- 개인: 순위, 선수명, 회원번호(동명이인일 때만), 경기 수, 승, 패, 승률
- 조합: 순위, 두 선수, 경기 수, 승, 패, 승률, `경기 수 적음` 배지

정렬은 `승률 내림차순 → 승리 수 내림차순 → 경기 수 내림차순 → 표시 이름 오름차순`이다. 경기가 없는 선수는 개인 순위 하단에 0경기, 0승, 0패, 0%로 표시한다. 조합은 한 경기 이상 존재할 때 생성한다.

### 3.5 선수 관리

선수 추가 시 표시 이름과 선택적 메모를 입력한다. 시스템이 `P001`, `P002` 형식의 변경 불가능한 회원번호를 자동 발급한다. 같은 이름을 허용하고, 동명이인이 두 명 이상일 때만 선택 목록과 순위에 `이름 · P001`처럼 표시한다. 비활성 선수는 새 경기 선택 목록에서 제외하지만 과거 기록과 통계에는 남긴다.

## 4. 시스템 아키텍처

### 4.1 구성

- **Next.js App Router PWA**: 모바일 UI, 서버 컴포넌트 기반 조회, 클라이언트 입력 폼, 설치 가능한 웹앱, 운영자 세션 및 쓰기 Route Handler 제공
- **Supabase Postgres**: 선수, 세션, 경기, 참가자, 동기화 작업의 원본 저장소
- **Supabase RPC**: 경기 생성·수정·취소를 하나의 데이터베이스 트랜잭션으로 처리
- **Supabase Realtime Broadcast**: 데이터베이스 트리거가 완료 경기 변경 이벤트를 채널에 발행하고 클라이언트가 관련 목록과 순위를 다시 조회
- **Supabase Edge Function**: Database Webhook의 즉시 호출과 1분 주기 예약 호출을 받아 동기화 대기 작업을 Google Sheets API로 전송
- **Google Sheets**: 경기별 한 행과 동기화 메타데이터를 보관하는 읽기·백업용 미러

통계 숫자는 쓰기 시 별도 누적하지 않는다. 완료 상태의 경기와 참가자 데이터를 기반으로 SQL 뷰에서 계산한다. 이 방식은 경기 수정과 취소가 발생해도 개인 및 조합 순위를 동일한 원본에서 다시 계산하므로 누적값 불일치를 막는다.

### 4.2 데이터 흐름

1. 앱이 `record_match` RPC에 선수 UUID 4개, 승리팀, 세션 날짜, 클라이언트 요청 ID를 보낸다.
2. RPC가 선수 활성 상태, 네 UUID의 고유성, 팀별 2명, 승리팀 값을 검증한다.
3. 같은 트랜잭션에서 세션을 찾거나 생성하고, 경기·참가자·시트 동기화 작업을 저장한다.
4. 커밋 후 데이터베이스 트리거가 Supabase Realtime Broadcast 채널에 세션별 변경 이벤트를 발행한다.
5. 앱은 오늘 기록, 개인 순위, 조합 순위 쿼리를 무효화하고 다시 조회한다.
6. 동기화 작업 생성 Webhook이 Edge Function을 즉시 호출한다. 호출 누락과 재시도를 보완하기 위해 예약 작업도 1분마다 같은 Edge Function을 호출한다.
7. Edge Function은 `FOR UPDATE SKIP LOCKED` 방식의 RPC로 실행 시각이 된 작업을 선점한 뒤 Google Sheets에 행을 추가하거나 기존 행을 수정한다.
8. 실패하면 재시도 횟수와 다음 실행 시각을 기록하며 앱에는 `동기화 대기`가 표시된다. 순위 계산에는 영향을 주지 않는다.

## 5. 데이터 모델

### 5.1 `players`

| 열 | 형식 | 규칙 |
|---|---|---|
| `id` | uuid | 기본 키 |
| `member_code` | text | 유일, `P` + 3자리 이상 연속 번호 |
| `display_name` | text | 앞뒤 공백 제거, 빈 값 금지 |
| `note` | text nullable | 운영자 메모 |
| `is_active` | boolean | 기본값 true |
| `created_at` | timestamptz | 생성 시각 |

`display_name`에는 유일 제약을 두지 않는다. 이름 변경은 과거 전적의 동일성을 바꾸지 않는다.

### 5.2 `sessions`

| 열 | 형식 | 규칙 |
|---|---|---|
| `id` | uuid | 기본 키 |
| `session_date` | date | 한국 시간 기준 날짜, 유일 |
| `status` | enum | `open`, `closed` |
| `created_at` | timestamptz | 생성 시각 |

하루를 하나의 세션으로 간주한다. 날짜가 바뀌면 첫 경기 저장 시 새 세션을 자동 생성한다.

### 5.3 `matches`

| 열 | 형식 | 규칙 |
|---|---|---|
| `id` | uuid | 기본 키 |
| `session_id` | uuid | `sessions.id` 외래 키 |
| `match_no` | integer | 세션 안에서 유일, 1부터 증가 |
| `winner_team` | enum | `A`, `B` |
| `status` | enum | `completed`, `cancelled` |
| `client_request_id` | uuid | 유일, 중복 제출 방지 |
| `played_at` | timestamptz | 실제 경기 기록 시각 |
| `updated_at` | timestamptz | 마지막 수정 시각 |

### 5.4 `match_participants`

| 열 | 형식 | 규칙 |
|---|---|---|
| `match_id` | uuid | `matches.id` 외래 키 |
| `player_id` | uuid | `players.id` 외래 키 |
| `team` | enum | `A`, `B` |
| `seat` | smallint | 팀 안에서 1 또는 2 |

기본 키는 `(match_id, player_id)`로 두어 한 선수가 같은 경기에 중복 출전하지 못하게 한다. `(match_id, team, seat)`에도 유일 제약을 두어 정확히 네 자리만 생성한다. 경기 참가자 변경은 `update_match` RPC만 허용한다.

### 5.5 `sheet_sync_jobs`

| 열 | 형식 | 규칙 |
|---|---|---|
| `id` | uuid | 기본 키 |
| `match_id` | uuid | 유일, 경기당 작업 한 행을 최신 상태로 병합 |
| `operation` | enum | `upsert`, `cancel` |
| `status` | enum | `pending`, `processing`, `succeeded`, `failed` |
| `attempt_count` | integer | 기본값 0 |
| `next_attempt_at` | timestamptz | 지수 백오프 실행 시각 |
| `sheet_row` | integer nullable | 최초 성공 후 행 번호 저장 |
| `match_version` | integer | 경기 수정 때마다 증가, 오래된 처리 결과 덮어쓰기 방지 |
| `last_error` | text nullable | 비밀정보를 제외한 오류 요약 |
| `updated_at` | timestamptz | 상태 변경 시각 |

## 6. 통계 계산

### 6.1 개인 순위 뷰

`completed` 경기의 참가자마다 한 행을 펼쳐 승리팀과 참가자 팀이 같으면 1승, 다르면 1패로 계산한다. 선수별로 다음 값을 집계한다.

- `games = wins + losses`
- `win_rate = wins / games`, 단 `games = 0`이면 0
- 화면 표시는 소수점 첫째 자리까지 반올림한 백분율

정렬에는 반올림 전 값을 사용해 표시값이 같은 선수도 실제 비율에 따라 정확히 정렬한다.

### 6.2 파트너 조합 순위 뷰

각 팀의 두 선수 UUID를 사전순으로 정렬해 `player_low_id`, `player_high_id`를 만든다. 따라서 선수 선택 순서가 달라도 같은 조합이다. 팀이 승리팀이면 조합에 1승, 아니면 1패를 부여한다. `games < 3`이면 `is_small_sample = true`를 반환한다.

예를 들어 첫 경기에서 `김재민 + 김민재`가 승리하고, 다음 경기에서 `김재민 + 재민김`이 승리했다면 김재민 개인 기록은 2승이며 두 파트너 조합은 각각 1승으로 별도 집계된다.

## 7. Google Sheets 동기화

시트는 `경기기록` 탭을 사용하고 다음 열을 고정한다.

`match_id`, `날짜`, `경기번호`, `경기시각`, `A팀1_회원번호`, `A팀1_이름`, `A팀2_회원번호`, `A팀2_이름`, `B팀1_회원번호`, `B팀1_이름`, `B팀2_회원번호`, `B팀2_이름`, `승리팀`, `상태`, `최종수정시각`, `동기화시각`

- 모든 작업은 먼저 `match_id` 열을 검색한다. 기존 행이 없을 때만 다음 빈 행에 추가하고, 있으면 그 행을 갱신한다. 따라서 Google 응답 유실 후 재시도해도 중복 행을 만들지 않는다.
- 수정은 저장된 행 번호와 `match_id`를 함께 확인한 후 같은 행을 갱신한다.
- 취소는 행을 삭제하지 않고 `상태=취소`로 바꾼다.
- 시트에서 사람이 셀을 수정해도 Supabase로 역동기화하지 않는다.
- 행 번호가 맞지 않으면 `match_id` 열을 검색해 복구한 뒤 갱신한다.
- 수정이 연속으로 발생하면 `match_id`가 유일한 동기화 작업 한 행의 `match_version`과 내용을 최신 버전으로 올린다. 처리 중 더 새 버전이 생기면 오래된 성공 결과로 작업을 완료하지 않고 최신 버전을 다시 처리한다.
- 서비스 계정 자격 증명과 시트 ID는 Edge Function 비밀 값으로만 보관한다.

재시도는 1분, 5분, 30분, 2시간 간격으로 수행하고 이후에는 `failed`로 남긴다. 운영자가 앱에서 수동 재시도를 실행할 수 있다. 동기화 실패는 경기 저장 성공을 되돌리지 않는다.

## 8. 실시간성과 캐시

`matches`와 `match_participants`의 변경 트리거가 세션별 비공개 Realtime Broadcast 채널에 `match_changed` 이벤트를 보낸다. 클라이언트는 원시 Postgres Changes를 직접 구독하지 않는다. 이벤트 자체의 내용을 로컬 통계에 더하지 않고, 서버 쿼리 키를 무효화해 다시 조회한다. 이 방식은 이벤트 중복이나 순서 뒤바뀜에도 최종 결과가 데이터베이스와 일치한다.

앱 재접속, 브라우저 백그라운드 복귀, 날짜 변경 시에도 오늘 세션과 순위를 다시 조회한다. Realtime 연결이 끊기면 화면에 `새로고침 필요` 상태를 표시하고 자동 재연결하며, 수동 새로고침도 제공한다.

## 9. 권한과 보안

- 공개 사용자는 완료 경기와 순위를 읽을 수 있다. 비공개 Broadcast 채널은 읽기 전용 익명 세션에도 구독 권한을 부여하되 쓰기 권한은 부여하지 않는다.
- 운영자는 서버 환경 변수의 공유 접근 코드를 Next.js Route Handler에 제출한다. 서버는 일정 횟수 실패 시 일시 차단하고, 성공하면 12시간 유효한 서명·HttpOnly·Secure·SameSite=Lax 쿠키를 발급한다.
- 선수 추가, 경기 생성·수정·취소, 동기화 재시도 Route Handler는 이 쿠키를 검증한 후 서버 전용 Supabase 자격으로만 RPC를 호출한다. RPC 실행 권한은 브라우저의 `anon`과 일반 `authenticated` 역할에서 회수한다.
- 브라우저에는 Supabase 익명 키만 제공하고 서비스 역할 키와 Google 자격 증명은 제공하지 않는다.
- 테이블 직접 쓰기는 RLS로 차단하고 변경은 검증 RPC를 통해 수행한다.
- RPC는 입력 UUID 개수, 활성 선수, 중복 선수, 팀 정원, 허용된 상태 전이를 데이터베이스에서 다시 검증한다.

초기 운영용 접근 코드는 소규모 동호회용 최소 인증이다. 개인별 계정과 사용자별 감사 추적은 MVP 범위 밖이며, 필요해지면 쓰기 Route Handler의 세션 발급부만 Supabase Auth 기반 운영자 계정으로 교체할 수 있도록 경계를 둔다.

## 10. 오류 처리와 데이터 정합성

- 저장 중 네트워크 오류가 나면 같은 `client_request_id`로 재시도해 중복 경기를 만들지 않는다.
- 중복 선수, 비활성 선수, 잘못된 승리팀은 RPC가 명확한 오류 코드로 거절한다.
- 경기 생성과 참가자 4명, 동기화 작업 생성 중 하나라도 실패하면 전체 트랜잭션을 롤백한다.
- 수정과 취소 후에는 같은 경기의 동기화 작업을 `pending`으로 되돌린다.
- 취소 경기와 미완성 데이터는 모든 순위와 당일 완료 경기 수에서 제외한다.
- Google Sheets 장애 시 앱에는 `동기화 대기` 또는 `동기화 실패`를 표시하되 Supabase 기록과 순위는 정상 제공한다.
- Sheets 행 추가가 성공한 직후 네트워크 응답이 유실되어도 다음 시도는 `match_id`를 먼저 검색하므로 같은 경기를 두 줄로 추가하지 않는다.

## 11. 검증 전략과 인수 기준

### 데이터베이스 테스트

- 네 선수가 모두 다를 때만 경기 생성에 성공한다.
- 같은 `client_request_id` 재전송은 새 경기를 만들지 않고 기존 결과를 반환한다.
- 팀당 두 명, 경기당 네 명 제약을 우회할 수 없다.
- 경기 수정과 취소 후 개인 및 조합 집계가 즉시 원래 기록에서 재계산된다.
- 선수 UUID 순서가 달라도 동일 파트너 조합으로 집계된다.
- 동명이인은 서로 다른 UUID와 회원번호로 독립 집계된다.

### 애플리케이션 테스트

- 네 선수를 선택하기 전에는 저장할 수 없다.
- 한 자리에 선택한 선수는 다른 자리에서 선택할 수 없다.
- 승리팀 확인 후 기록 화면에 둥근 승리팀 강조와 `승` 배지가 표시된다.
- 개인/파트너 탭 전환, 날짜 변경, 빈 상태, 오류 상태가 모바일 화면에서 동작한다.
- 파트너 조합 1~2경기에는 `경기 수 적음`이 보이고 3경기부터 사라진다.

### 통합 테스트

- 한 휴대폰에서 저장한 경기가 다른 휴대폰의 기록과 두 순위표에 자동 반영된다.
- 경기 저장 후 Google Sheets에 정확히 한 행만 생성된다.
- 시트 API 실패 후 재시도하면 중복 행 없이 기존 작업이 성공한다.
- 시트 행 추가 성공 직후 응답 유실을 재현해도 `match_id`당 행이 정확히 하나만 남는다.
- 경기를 수정하거나 취소하면 시트의 동일 `match_id` 행이 갱신된다.

### 완료 기준

1. 복식 경기 입력부터 개인·조합 순위 반영까지 일반 모바일 네트워크에서 별도 새로고침 없이 동작한다.
2. 파트너 변경이 개인 기록을 분리하지 않고, 조합 기록은 파트너별로 정확히 나뉜다.
3. 동명이인 추가 후에도 기존 및 신규 기록이 회원번호와 UUID로 섞이지 않는다.
4. 시트 동기화 장애가 경기 저장이나 순위 조회를 막지 않으며 재시도 상태를 확인할 수 있다.
5. 경기 수정·취소 후 앱과 Google Sheets가 같은 최종 상태에 도달한다.

## 12. 구현 단계 경계

구현은 다음 순서로 계획한다.

1. Next.js PWA 골격과 테스트 환경
2. Supabase 스키마, 제약, RLS, 통계 뷰, 경기 RPC
3. 선수 관리 및 경기 입력 화면
4. 오늘 기록과 개인·파트너 순위 화면
5. Realtime 갱신과 연결 상태 처리
6. Google Sheets 동기화 Edge Function과 재시도
7. 수정·취소, 통합 테스트, 모바일 접근성 및 배포 검증

이 문서는 설계 기준이며 구현 코드를 포함하지 않는다. 상세 구현 계획까지 Sol 모델로 작성한 뒤, 실제 코드 개발을 시작하기 직전에 작업을 멈추고 사용자에게 Luna 모델 전환을 요청한다.
